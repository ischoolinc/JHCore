## 1. 摘要

前四輪優化（見 `openspec/changes/archive/`）已處理啟動流程中最明顯的成本：背景同步、課程限定學期、XML 解析、延後非主要面板的 `SetupPresentation()`；本分支也已加入「收合面板不載入」。

這次逐檔檢視後，剩下的瓶頸大多不在啟動的那一瞬間，而在下面三個地方：

1. **切換記錄時，詳細資料面板每次都重新抓「整張表」**。教師基本資料、教師帶班、班級基本資料三個面板，在每次選取變更時都呼叫 `SelectAll()`，把全校教師或全校班級重新下載一次，只為了做重複檢查或找出一兩筆資料。這些資料早已在記憶體快取（`Teacher.Instance`、`Class.Instance`）中。
2. **學生清單載入全部歷史學生**。`GetAllStudents()` 不分狀態，連同歷年畢業、刪除的學生一起載入，但預設篩選只顯示「一般」。學校越老，這部分的比例越高。
3. **存檔／刪除後觸發全量重新同步**。刪除一位學生會重新載入全部學生；儲存教師會重新載入全部班級；學生存檔前會用 `JHStudent.SelectAll()` 取回全校學生完整資料來檢查重複。

另外發現一個**功能性回歸**：課程的學期篩選選單是從已載入的課程中蒐集學期，而課程現在只載入預設學期，因此使用者**無法切換到其他學期**（見 E1）。建議優先修正。

建議的執行順序：

| 階段 | 內容 | 風險 | 預估工時 |
|---|---|---|---|
| P0 | 加入計時記錄，建立基準數據；修正課程學期選單回歸 | 低 | 1 天 |
| P1 | 面板改用記憶體快取、存檔後改為局部同步、清單欄位去除重複配置 | 低 | 2–3 天 |
| P2 | 學生分段載入、UI 執行緒同步呼叫移出、照片延後載入、選取防抖 | 中 | 3–5 天 |
| P3 | 清單查詢改走 SQL、本機快取 | 中高 | 需另行評估 |

> **說明：本報告是靜態程式碼分析的結果，沒有實測數據。** 文中「影響」欄位是根據呼叫次數與資料量推估的相對大小，不是量測值。P0 的計時記錄是後續所有判斷的前提，建議先做。

## 2. 現況：載入流程

```
Program.Main()（UI 執行緒）
├─ Framework.Program.Initial()                ← 原註解記載約 1 秒，外部 DLL
├─ School.Configuration = ...
├─ Class/Student/Teacher/Course.SyncAllBackground()   ← 四個背景執行緒同時發出
│    └─ Course.Instance 建構時讀取 GlobalOld.SystemConfig（UI 執行緒）
├─ Student.SetupPresentation()                ← 同步；讀取 2 個 User.Configuration
├─ Application.Idle → Class/Teacher/Course.SetupPresentation()（延後）
├─ Task.Run → Aspose 授權
├─ ApplicationLog.Log("登入")                 ← UI 執行緒同步寫入
└─ 開始選單、權限、狀態列

資料到達後（ItemLoaded）
└─ SetSource → FillFilter → 清單重繪 → NavView.Layout

使用者點選一筆記錄
└─ 每個已註冊且展開的 DetailContent → BackgroundWorker → 後端查詢
```

## 3. 問題清單

每項都列出位置、現象、建議做法。代號對應第 4 節的路線圖。

### A. 啟動階段

#### A1. 學生清單載入全部歷史學生（影響：高）

- 位置：[Feature/QueryStudent.cs:63-77](../Feature/QueryStudent.cs#L63-L77)
- 現象：`GetAllStudents()` 的 `Condition` 是空的，所有狀態（一般、休學、輟學、畢業或離校、刪除）的學生都會下載並建立 `StudentRecord`。預設篩選只勾「一般」（[Student.cs:711-712](../Student.cs#L711-L712)）。一所設校十年以上的國中，畢業生通常是在校生的數倍。
- 另外，使用的服務是 `GetAbstractListWithTag`，但 Tag 相關欄位已全部註解掉（[QueryStudent.cs:53-57](../Feature/QueryStudent.cs#L53-L57)），回傳內容中的類別資訊沒有被使用。
- 建議：**分段載入**。
  1. 第一段只載入在校狀態（一般、休學、輟學），載完就觸發 `ItemLoaded`，讓清單先出現。
  2. 第二段在背景補齊畢業或離校、刪除，完成後再觸發一次 `ItemUpdated`。
  3. 若服務的 `Condition` 不支援狀態條件，改用 `FISCA.Data.QueryHelper` 以 SQL 查詢 `student` 表（狀態欄位的數值對應需先確認）。
- 注意：其他模組可能直接讀 `Student.Instance.Items[id]` 取得畢業生。採分段載入（最終仍會載入全部）而非「按需載入」，就是為了不破壞這個假設。第二段完成前的短暫空窗需要確認沒有模組在啟動時就讀取畢業生。

#### A2. UI 執行緒上的同步網路呼叫（影響：中，需實測）

以下呼叫發生在 `Main()` 或其直接呼叫的路徑上，若底層是同步網路請求，會直接延後視窗出現：

| 位置 | 呼叫 |
|---|---|
| [Program.cs:83](../Program.cs#L83) | `FISCA.LogAgent.ApplicationLog.Log("[特殊歷程]", "登入", ...)` |
| [Course.cs:30](../Course.cs#L30) | 欄位初始化讀取 `School.DefaultSchoolYear/DefaultSemester`（`GlobalOld.SystemConfig`），在 `Program.cs:31` 建立 `Course.Instance` 時於 UI 執行緒執行 |
| [Student.cs:721](../Student.cs#L721)、[Student.cs:509](../Student.cs#L509) | `User.Configuration["DefaultFiltersPreference"]`、`["StudentSearchOptionPreference"]` |

- 建議：
  - 登入記錄改為 `Task.Run(() => ApplicationLog.Log(...))`，失敗只寫 Trace，不影響登入。
  - P0 的計時記錄先確認 `User.Configuration[...]` 與 `GlobalOld.SystemConfig` 是否已在 `Framework.Program.Initial()` 中快取。若沒有，在 `Main()` 開頭以背景工作預先讀取。

#### A3. 沒有效能量測（影響：間接）

- 現況：專案中沒有任何 `Stopwatch` 或計時記錄，四輪優化都沒有留下前後對照數據。
- 建議：見第 5 節。

### B. 切換記錄（詳細資料面板）

這一類是使用者每天最常感受到的延遲：在清單上每點一筆，就要等面板載入。

#### B1. 教師基本資料：每次選取都下載全部教師（影響：高）

- 位置：[TeacherExtendControls/BaseInfoItem.cs:173-198](../TeacherExtendControls/BaseInfoItem.cs#L173-L198)
- 現象：`_BGWork_DoWork` 每次都執行 `JHTeacher.SelectAll()`，建立姓名、登入帳號、身分證號、教師編號四個字典。這四個字典**只在按下儲存時使用**（`OnSaveButtonClick`）。
- 建議：
  - `DoWork` 只保留 `JHTeacher.SelectByID(PrimaryKey)`。
  - 重複檢查移到存檔時，以 SQL 精準查詢，例如：
    `select id from teacher where lower(st_login_name) = @login and id <> @id`
  - 或在存檔時改用 `Teacher.Instance.Items`（記憶體中已有姓名、暱稱、身分證號、登入帳號）。

#### B2. 班級基本資料：每次選取都下載全部班級與全部教師（影響：高）

- 位置：[ClassExtendControls/ClassBaseInfoItem.cs:254-272](../ClassExtendControls/ClassBaseInfoItem.cs#L254-L272)
- 現象：`JHClass.SelectAll()` 與 `JHTeacher.SelectAll()` 每次都執行，用來做班名重複檢查和班導師下拉選單。
- 建議：班名清單改用 `Class.Instance.Items`；教師名稱改用 `Teacher.Instance.Items`（過濾狀態「刪除」）。`DoWork` 只保留 `JHClass.SelectByID(PrimaryKey)`。

#### B3. 教師帶班班級：全部班級 + 每班學生（影響：高）

- 位置：[TeacherExtendControls/TeachStudentItem.cs:96-101](../TeacherExtendControls/TeachStudentItem.cs#L96-L101)
- 現象：先 `JHClass.SelectAll()` 再逐一比對 `RefTeacherID`，接著在 UI 執行緒的 `BindDataToForm()` 中讀取 `classRec.Students`，計算男女人數。若 `JHClassRecord.Students` 是延遲查詢的屬性，就會變成每班一次查詢（N+1），而且是在 UI 執行緒上。
- 建議：全部改用記憶體快取。
  - `Class.Instance.GetTecaherSupervisedClass(teacher)` 取得帶班班級。
  - `Student.Instance.GetClassStudents(classRec)` 取得學生；`StudentRecord` 已有 `Gender` 與 `Status`。
  - 整個面板不需要任何網路請求，也可以拿掉 BackgroundWorker。

#### B4. 學生基本資料：三次循序請求，含兩張照片（影響：中）

- 位置：[StudentExtendControls/BaseInfoPalmerwormItem.cs:278-287](../StudentExtendControls/BaseInfoPalmerwormItem.cs#L278-L287)
- 現象：依序呼叫 `SelectFreshmanPhoto`、`SelectGraduatePhoto`、`JHStudent.SelectByID`。照片是 base64 字串，通常是三者中最大的；文字欄位要等兩張照片都下載完才會顯示。
- 建議：拆成兩段。先載 `SelectByID` 並立即綁定文字欄位，再另開一個工作載入照片後補上。或至少用 `Task.WhenAll` 讓三個請求並行。

#### B5. 選取變更沒有防抖（影響：中）

- 現況：openspec `module-loading-performance-analysis` 的任務 2 尚未實作。
- 評估：現有面板的 `_isBGWorkBusy` 模式在忙碌時只記一個旗標，完成後補跑一次，所以快速捲動時每個面板最多跑「目前這次 + 最後一次」。防抖能省下的是第一次的那個中間請求，效益比原設計文件預期的小。
- 建議：
  - FISCA 是直接設定面板的 `PrimaryKey`，在 `LegacyPresentBase` 層攔截不到面板的載入。建議在面板層處理：抽出一個共用基底（或 helper），在 `OnPrimaryKeyChanged` 中啟動 150 ms 的 `System.Windows.Forms.Timer`，Tick 時才 `RunWorkerAsync()`。
  - 優先級排在 B1–B4 之後，因為 B1–B3 修完後，每次載入本身就已經很便宜。

#### B6. 延遲載入的涵蓋範圍（已完成，記錄限制）

- c495642 只涵蓋本專案的 5 個面板，以及透過 `ContentItemBulider` 包裝的舊式面板。其他模組（外掛）註冊的 `DetailContent` 仍會在收合時載入。若要全面受惠，需要在 FISCA 框架層實作，或提供共用基底給其他模組採用。

### C. 清單與導覽檢視繪製

清單每列、每次重繪、每次排序都會呼叫 `GetVariable`，所以這裡的小成本會被放大。

#### C1. 班級清單「人數」欄位每列複製一份學生清單（影響：中）

- 位置：[Class.cs:261-269](../Class.cs#L261-L269) → [ClassRecord.cs:50](../ClassRecord.cs#L50) → [Student.cs:183-195](../Student.cs#L183-L195)
- 現象：`Items[e.Key].Students.Count` 每次呼叫都會 `lock` 並 `new List<StudentRecord>(...)` 複製整班學生，只為了取得 `Count`。排序時每次比較都會觸發。
- 建議：在 `Student` 新增 `GetClassStudentCount(string classId)`，在 lock 內直接回傳 `Count`，不配置新清單。

#### C2. 教師清單「帶班班級」欄位每列重新組字串（影響：低–中）

- 位置：[Teacher.cs:188-198](../Teacher.cs#L188-L198)
- 現象：每列呼叫 `GetTecaherSupervisedClass`（複製清單），再以字串串接組出班名。
- 建議：在 `Class` 的索引建立時，順便建立 `teacherId → "班名1、班名2"` 的快取字串，`ItemLoaded/ItemUpdated` 時失效。

#### C3. 其他小項（影響：低）

- [Student.cs:404-475](../Student.cs#L404-L475)：每個欄位的 `GetVariable` 都先 `Items[e.Key] != null` 再取一次 `Items[e.Key]`，可改為取一次存區域變數。
- [Student.cs:834](../Student.cs#L834)：搜尋結果用 `List.Contains` 去重，結果多時是 O(n²)，改用 `HashSet<string>`。
- 導覽檢視（`GradeYear_Class_View` 等）建樹時，可加上 `advTree1.BeginUpdate()/EndUpdate()` 減少重繪。

### E. 功能性風險

#### E1. 課程學期篩選選單無法切換學期（回歸，需優先修正）

- 位置：[Course.cs:315-358](../Course.cs#L315-L358)
- 現象：選單的學期清單是從 `Items` 蒐集的。自從 2026-03-14 改為只載入預設學期後，`Items` 裡只有一個學期，選單也就只會出現這一個選項。切換學期並重新載入的程式碼（第 346-351 行）存在，但使用者無從觸發。
- 建議：學期清單改由後端取得，例如：
  `select distinct school_year, semester from course order by school_year desc, semester desc`
  在背景查詢後快取；選單開啟時若尚未取回，至少顯示目前學期。

#### E2. `Course.Instance.Items` 只含單一學期

- 更正：`Framework.CacheManager` 的 `Items[id]` 在鍵值不存在時會同步呼叫 `GetData` 補抓該筆，所以以 `Course.Instance[id]` 取非預設學期的課程**不會**拿到 `null`，只是多一次同步查詢。
- 仍需注意的是**列舉** `Course.Instance.Items` 的程式（例如「取某學期的所有課程」），只會看到已載入的學期。建議盤點外部模組是否有此用法。A1 若採「按需載入」也有同樣的限制，所以 A1 仍建議採分段載入。

#### E3. 檔案編碼（工程風險）

- 本專案部分 `.cs` 檔是 Big5（例如 `TeacherExtendControls/BaseInfoItem.cs`、`TeachStudentItem.cs`、`TeachCourseItem.cs`），其餘是 UTF-8。本分支上一次修改時，這兩個 Big5 檔曾被誤存為 UTF-8，導致中文字串與 `FCode` 權限名稱損毀，已在 c495642 修復。
- B1–B3 都要修改這些 Big5 檔。建議在動手前，以獨立 commit 將它們統一轉為 UTF-8 with BOM（Visual Studio 可正確讀取），避免再次發生。

## 5. 量測計畫

建議在以下時間點以 `System.Diagnostics.Stopwatch` 記錄，輸出到 `Trace` 或本機檔案（例如 `%TEMP%\JHSchool_perf.log`），並以編譯常數或設定值控制開關：

| 指標 | 起點 | 終點 |
|---|---|---|
| T1 `Main()` 總耗時 | `Main()` 開始 | `Main()` 結束 |
| T2 `Framework.Program.Initial()` | 呼叫前 | 呼叫後 |
| T3 各實體 `GetAllData()` | 方法開始 | 方法結束（分網路與解析兩段） |
| T4 學生清單可操作 | `Main()` 開始 | `Student` 的 `ItemLoaded` 後 `FillFilter()` 完成 |
| T5 延後面板設定 | Idle 委派開始 | 結束 |
| T6 面板載入 | `OnPrimaryKeyChanged` | `RunWorkerCompleted` 綁定完成（每個面板分開記錄） |
| 筆數 | — | 各實體載入筆數、學生依狀態的分布 |

建議至少在兩種環境量測：小型學校（約 500 名學生）與大型、設校久的學校（數千名在校生加上大量畢業生）。A1 的效益取決於畢業生比例，需要用後者的數據來判斷。

## 6. 相容性與注意事項

- **IRewriteAPI 覆寫**：學生、班級、教師的基本資料面板可能被 `IRewriteAPI_JH` 的實作取代（如高雄版本）。B1–B4 只改得到本專案的預設面板，覆寫版本需由該模組各自處理。
- **外部模組對快取內容的假設**：A1、E2 都涉及 `*.Instance.Items` 的內容範圍。修改前建議以全文搜尋盤點其他 JH 模組對 `Student.Instance`、`Course.Instance` 的使用方式。
- **記憶體快取的新鮮度**：B1–B3 改用記憶體快取後，資料新鮮度取決於 `SyncDataBackground` 是否在每次異動後正確觸發。D 類的修改正好會讓局部同步更準確；兩者應一起驗證。
- **權限**：所有修改都不影響 `FCode`／`FeatureCode` 的註冊與檢查。
